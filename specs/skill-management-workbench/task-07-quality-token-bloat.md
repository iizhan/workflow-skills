# TASK-07 质量评分、Token 预算与臃肿治理协议

## 1. 文档状态

- 任务：`TASK-07`
- 版本：`1.0.0`
- 状态：`accepted`
- 接受时间：`2026-07-14`
- 影响等级：`high`
- 前置任务：`TASK-01` 至 `TASK-06`
- 目标：建立可解释的 Skill/Workflow/项目质量评估、Token 成本预算、分级熔断和结构臃肿治理体系。

本任务定义评分和治理协议，不立即修改用户 Skill，不自动删减项目文件，不宣称本地应用可以跨设备强制执行团队预算。

## 2. 当前问题

当前实现已有 `health_score_policy`、Skill 健康分、每日/每周指标和优化建议，但仍存在几个产品风险：

- 一个总分同时承载规范、可靠性、成本、延迟、新鲜度和维护性，用户看不出分数为什么变化；
- 没有明确区分静态分析分、运行质量分、证据置信度和样本覆盖率；
- Token 字段混合了真实值、Adapter 值、日志解析值和本地估算值，存在重复累计风险；
- 没有个人会话、项目共享、前台会话、后台巡检的预算池隔离；
- 阈值散落在代码或隐含在 UI 中，无法按项目技术栈和团队约束配置；
- Skill、目录和 Workflow 的臃肿没有统一测量单位、等级和处理边界；
- “自动精简规则”如果直接改写运行中的 Skill，可能改变语义、绕过确认并造成回归。

## 3. 总体原则

1. **分维度，不迷信总分**：总分是摘要，维度分、证据和覆盖率才是诊断依据。
2. **质量与证据绑定**：没有足够样本时显示未知或低置信度，不用默认值伪造好成绩。
3. **真实 Token 优先，估算 Token 只做估算**：同一 Run 的 provider、Adapter、日志和本地估算不得重复相加。
4. **预算先检查、再执行**：启动前做预估，运行中做累计，接近边界时反馈并暂停后续节点。
5. **后台任务独立记账**：后台监控和巡检不能悄悄消耗前台会话预算。
6. **治理不等于静默改写**：臃肿发现生成提案或草稿，只有安全的只读加载优化可自动生效。
7. **项目策略是共享真值**：项目级阈值写入项目配置并跟随 Git；个人 UI 偏好只能改变展示，不能偷偷改变项目门禁。
8. **阻断要可恢复**：阻断新增或激活，不删除已有能力；必须给出原因、影响、修复路径和例外审批入口。

## 4. 评估对象与时间窗口

评估对象分为三层：

| 对象 | 评估内容 | 典型用途 |
| --- | --- | --- |
| Skill / Skill Version | 规范、可用性、健康、Token 效率、臃肿、项目适配 | Skill 库排序、版本对比、优化提案 |
| Workflow / Workflow Version | 节点结构、路径成功率、门禁、重试、Token、偏差 | 流程报告、发布前检查、流程拆分 |
| Project | Skill/Workflow 总体健康、预算、趋势、阻断项 | 项目管理、总览建议和心跳报告 |

每份评估必须声明窗口：

- `current_run`：当前一次运行；
- `last_24h`：最近 24 小时；
- `last_7d`：最近 7 天；
- `last_30d`：最近 30 天；
- `baseline`：用户选择的历史基线；
- `historical`：明确标记的归档报告，不影响当前决策。

默认展示 `last_7d`，没有有效运行证据时展示静态评估和“等待运行证据”，而不是将静态分冒充运行健康。

## 5. 六维质量模型

### 5.1 维度与默认权重

初始权重用于项目默认模板，允许通过版本化策略调整，但每次调整都要保留旧报告可重算的策略引用。

| 维度 | 默认权重 | 衡量内容 |
| --- | ---: | --- |
| `compliance` 规范性 | 30% | 入口、Schema、命名、输入输出、权限、厂商/项目规则符合度 |
| `usability` 可用性 | 25% | 用例通过率、成功率、失败可解释性、重试和恢复能力 |
| `maintainability` 健康度 | 15% | 新鲜度、重复规则、依赖清晰度、可扩展性和变更风险 |
| `token_efficiency` Token 能效 | 15% | 业务有效产出代理指标与 Token 消耗的关系 |
| `compactness` 臃肿度 | 10% | 内容规模、结构深度、重复和无效路径 |
| `project_fit` 项目适配 | 5% | 与当前 Project Profile、技术栈、角色和任务场景的匹配 |

权重不是事实本身。报告必须同时显示各维度原始分、权重、证据数量、置信度和是否参与计算。

### 5.2 分数、置信度和覆盖率

每个维度输出：

```json
{
  "dimension": "usability",
  "score": 86,
  "confidence": 0.78,
  "sample_count": 24,
  "evidence_count": 61,
  "coverage": 0.92,
  "eligibility": "current",
  "reasons": ["24 次运行中 22 次成功"],
  "policy_version": "quality-policy-1.0"
}
```

规则：

- `score` 是 0-100 的标准化结果，不是成功概率；
- `confidence` 表示证据可信度，不是质量分；
- `coverage` 表示本维度所需信号实际获得的比例；
- 缺少必要信号时维度可以为 `null`，并显示 `unknown_reason`；
- 总分只有在最低覆盖率和最低样本条件满足时才显示；否则显示 `partial`，不强行补满 100 分；
- 计算总分时只对有资格的维度进行权重归一化，并同时显示未参与的维度；
- `precise` 证据优先于 `inferred`，当前证据优先于历史证据；
- 归档、低置信度、重复和被策略排除的证据不能偷偷进入当前评分。

### 5.3 可用性评分口径

优先使用：

1. 自动化用例通过率；
2. 精确运行成功率；
3. 有明确错误码和恢复路径的失败比例；
4. 重试后成功率和平均重试次数；
5. 用户确认的交付/验收反馈。

没有自动化用例或精确 Skill 事件时，可以使用推断证据，但必须降低置信度，并在报告中标注“无法证明精确调用”。

### 5.4 Token 能效口径

“有效产出 Token”不能直接从任意文本长度推导。MVP 使用可追溯代理信号：

- 用户确认的结果/验收事件；
- 验证报告通过的结果；
- 结构化工件是否生成且通过校验；
- 重复运行是否减少失败或返工；
- 总 Token、工具调用和运行时长。

没有有效产出证据时，只显示消耗和效率未知，不给出伪精确的 ROI。

## 6. Score Policy 配置

项目配置在 `.skill-os/project.yaml` 中声明，推荐结构：

```yaml
quality_policy:
  version: "1.0.0"
  preset: "balanced"
  dimensions:
    compliance: 0.30
    usability: 0.25
    maintainability: 0.15
    token_efficiency: 0.15
    compactness: 0.10
    project_fit: 0.05
  minimum_coverage: 0.60
  minimum_runtime_samples: 5
  evidence_window: "last_7d"
```

约束：

- 权重必须大于等于 0 且总和为 1；
- `minimum_coverage` 和样本要求必须可解释；
- 本地 SQLite 可以保存用户试算策略，但项目门禁使用项目文件中已确认版本；
- 修改策略生成 Preview，旧报告保留 `policy_version`；
- 质量策略不授予写项目、远程下载或运行 Harness 的权限。

## 7. Token 来源、账单和去重

### 7.1 来源等级

统一来源：

- `provider_reported`：Provider usage metadata，最高优先级；
- `harness_precise`：Harness/Adapter 精确事件；
- `structured_log`：结构化日志解析；
- `local_estimated`：本地分词器或规则估算；
- `manual`：人工录入，仅用于审阅或校正。

每个数值保存：`value`、`unit`、`source`、`confidence`、`observed_at`、`event_ref` 和 `estimation_method`。

### 7.2 同一 Run 去重

同一个 `run_id` 的 Token 归并顺序：

```text
provider_reported
  > harness_precise
  > structured_log
  > local_estimated
```

规则：

- provider 与估算值不能相加；
- prompt、completion、total 不得重复累计，`total` 缺失时才由前两者推导；
- 同一事件重导入必须幂等；
- 来源冲突保留冲突记录，并在报告中显示采用值和未采用值；
- 不同 Harness 并行运行必须使用不同 `budget_pool_id` 和 `run_namespace`。

### 7.3 静态 Token 预估

Skill/Workflow 激活前可计算规则、描述、引用和预期加载内容的 Token 估算。静态估算只用于预警和预算预检，不冒充运行账单。

固定内容的估算结果按内容哈希缓存；内容变化、分词器版本变化或策略变化时失效重算。

## 8. 双层预算与后台隔离

### 8.1 预算池

预算至少拆分为：

| 预算池 | 作用 | 典型阻断范围 |
| --- | --- | --- |
| `personal_session` | 当前用户/当前会话临时预算 | 当前会话新增节点或下一次调用 |
| `project_shared` | 项目周期内总预算 | 当前项目新的运行/后台任务 |
| `background_monitoring` | 心跳、巡检、导入、聚合 | 后台任务，不占前台会话 |
| `harness_instance` | 单个 Harness/Adapter 并行上下文 | 当前 Harness 实例 |

本地桌面端可以可靠执行本机预算和审计，但不能在没有共享协调服务的情况下宣称跨设备、跨成员的强一致 `project_shared` 硬阻断。团队预算策略可以写入 Git 并在各客户端提示/阻断本地执行，真实全局强制留给未来协作服务。

### 8.2 预算配置

```yaml
token_budget:
  version: "1.0.0"
  project_shared:
    period: "daily"
    soft_limit: 200000
    hard_limit: 240000
  personal_session:
    soft_limit: 30000
    hard_limit: 40000
  background_monitoring:
    soft_limit: 20000
    hard_limit: 30000
  alerts:
    warning_percent: 80
    critical_percent: 95
    exhausted_percent: 100
```

额度单位默认是 Token；成本预算可增加独立的 `usd` 币种，不用 Token 与金额混成一个字段。

### 8.3 预算生命周期

```text
preflight estimate
  → reserve provisional budget
  → start run
  → account observed usage
  → reconcile estimate/provider value
  → release unused reservation
  → close budget ledger
```

预估不应永久扣除额度。运行失败、取消或无事件时必须释放未使用预留，并保留审计。

### 8.4 告警和熔断动作

- 80%：提示用户当前预算、来源和预计剩余量；后台任务降低频率或排队。
- 95%：强提醒；新 Workflow 节点或大范围后台任务需要确认/暂停。
- 100%：停止启动新任务，已运行任务按 Harness 能力优雅收尾；不能强行杀死外部进程并伪造失败。
- 硬限额可由项目策略选择 `block` 或 `require_confirmation`；没有精确 Token 时只能对估算值做预警，不能据此声称真实额度已耗尽。

熔断状态：

- `normal`
- `warning`
- `critical`
- `exhausted`
- `paused`
- `reconciled`
- `unknown_usage`

## 9. 臃肿度检测模型

### 9.1 三类结构指标

目录臃肿：

- 最大目录深度；
- 单目录 Skill 数量；
- 重名和重复路径；
- 闲置内容占比；
- 无法归属项目/Workflow 的孤立能力。

Skill 臃肿：

- 文件行数和 Token 估算；
- 说明/规则重复度；
- 引用层级和加载深度；
- 重复条件和冲突规则；
- 单 Skill 承担的角色数量；
- 无效、过期或未引用的参考资料。

Workflow 臃肿：

- 节点数和最长路径；
- 最大分支 fan-out；
- 子流程嵌套深度；
- 重试次数；
- 重复 Skill 路径；
- 不可达、孤立、无出口节点；
- 声明/实跑偏差和回退比例。

### 9.2 默认阈值

以下是新项目的可配置默认值，不是所有技术栈的绝对标准：

| 指标 | 关注阈值 | 严重阈值 |
| --- | ---: | ---: |
| 目录最大层级 | 4 | 6 |
| 单目录 Skill 数量 | 20 | 40 |
| 单 Workflow 节点数 | 10 | 20 |
| Workflow 最大子流程嵌套 | 3 | 5 |
| 单节点最大重试次数 | 2 | 3 |
| 单分支最大 fan-out | 4 | 8 |
| Skill 文件行数 | 300 | 700 |

项目可以在 `.skill-os/project.yaml` 的 `bloat_policy` 中覆盖，并必须说明原因、适用范围和版本。阈值变化要进入项目配置差异和质量报告。

### 9.3 重复度计算

MVP 使用可解释的确定性方法：

- 规则 ID、标题和规范化文本的精确重复；
- 规范化句段的 token 集合 Jaccard 相似度；
- Workflow 节点路径的规范化序列比较；
- 同一 Skill/版本在多个路径重复加载的计数。

语义模型相似度可以作为未来辅助信号，但不能在 MVP 中单独触发删除、合并或阻断。

## 10. 臃肿分级与处理边界

### 10.1 轻度

触发关注阈值但没有明显运行退化：

- 在 Skill/Workflow 详情和总览建议中提示；
- 显示具体超限指标、影响范围和建议动作；
- 不修改内容，不阻断已有或新增运行。

### 10.2 中度

多个关注指标、重复规则明显或运行成本/延迟已经恶化：

- 生成拆分、引用外置、合并重复规则或减少加载范围的草稿；
- 给出预估 Token、延迟和风险变化；
- 新增节点或发布新 Workflow 版本时要求用户确认优化建议；
- 不自动覆盖正式 Skill/Workflow。

### 10.3 重度

达到严重阈值、存在不可达/无出口结构或预算风险：

- 阻止新的 Workflow 版本激活，或要求显式例外审批；
- 保留当前 active 版本用于观测，不删除、不静默拆分；
- 生成强制拆分/降载计划和回滚说明；
- 若只是历史项目已有问题，不因新版本升级自动破坏正常工作。

安全的自动动作仅包括：懒加载未命中引用、缓存静态 Token 估算、降低后台扫描频率和排队后台任务。任何会改变 Skill 语义、执行顺序或项目文件的动作都必须走 Preview-Confirm-Apply。

## 11. 评分、预算和臃肿的关系

三套结果不互相覆盖：

- 质量分回答“当前能力是否可靠、可维护、适配项目”；
- 预算状态回答“现在还能否安全执行”；
- 臃肿状态回答“结构是否正在拖慢或增加风险”。

例如：一个 Skill 可以质量分 90，但当前项目预算已耗尽；也可以质量分 65，但在低风险个人会话中仍允许执行。UI 必须同时展示，不使用单一颜色或单一总分替代这些状态。

## 12. 报告和界面交互

质量报告按项目、Workflow、Skill、Skill 版本和时间窗口过滤。每个指标可下探到：

- 原始证据事件或证据摘要；
- 运行/会话/项目；
- Token 来源和采用规则；
- 预算池、已用、预留、剩余和阈值；
- 臃肿指标具体路径；
- 关联建议、草稿和验证结果。

总览只显示需要处理的建议和每个项目的数量，不把所有历史建议无限纵向挤压最近活动。长列表支持分页或虚拟滚动，并显示项目名、时间和严重级别。

技能库支持按质量分、置信度、调用次数、Token、失败率、延迟、臃肿等级和更新时间排序/筛选。点击调用次数、Token 或评分进入详情下探，不直接跳离当前项目上下文。

## 14. 状态与错误码

| 错误码 | 含义 | 推荐动作 |
| --- | --- | --- |
| `QUALITY_EVIDENCE_INSUFFICIENT` | 样本或覆盖率不足 | 显示未知并等待更多证据 |
| `QUALITY_POLICY_INVALID` | 权重或阈值配置无效 | 修正配置并重新预览 |
| `TOKEN_SOURCE_CONFLICT` | 多来源 Token 值不一致 | 按优先级采用并查看冲突 |
| `TOKEN_BUDGET_RESERVATION_FAILED` | 无法预留本次预算 | 减少范围、等待或确认例外 |
| `TOKEN_BUDGET_EXHAUSTED` | 预算池已耗尽 | 暂停新任务或申请扩容 |
| `TOKEN_USAGE_UNKNOWN` | 运行没有可靠 Token 来源 | 只能显示估算/未知 |
| `BLOAT_POLICY_INVALID` | 臃肿策略格式无效 | 恢复上个有效策略 |
| `BLOAT_THRESHOLD_REACHED` | 达到关注或严重阈值 | 查看指标和治理建议 |
| `WORKFLOW_ACTIVATION_BLOCKED_BLOAT` | 臃肿风险阻止新版本激活 | 拆分、降载或提交例外审批 |
| `QUALITY_RECALCULATION_REQUIRED` | 策略或证据变化需重算 | 重建评估快照 |

## 15. 对现有实现的影响

后续实现预计涉及：

- 将 `health-score-service` 从单一扣分逻辑扩展为维度评分和置信度/覆盖率输出；
- 保留现有健康策略预设作为兼容入口，但底层记录策略版本和维度结果；
- 扩展 `skill_runs`、Metrics 和证据引用，区分 Provider/Adapter/日志/估算 Token；
- 新增前台、项目、后台和 Harness 实例预算池与账本；
- 在运行启动前增加预算预检、预留、对账和告警；
- 增加目录、Skill、Workflow 的臃肿扫描和结构化 findings；
- 将“自动精简”改为草稿/提案，禁止静默改写正式文件；

## 16. 验收标准

- [ ] Skill、Workflow、项目评估都能展示六个维度、维度分、置信度、覆盖率、样本和证据来源。
- [ ] 缺少运行证据时不会生成伪造的运行健康分。
- [ ] 质量策略权重、最低覆盖率、窗口和版本可配置且可追溯。
- [ ] Provider、Harness、日志和本地估算 Token 有来源和优先级，不会重复累计。
- [ ] 前台会话、项目共享、后台监控和 Harness 实例使用隔离预算池。
- [ ] 本地应用不会把跨设备/跨成员预算宣称为强一致全局限制。
- [ ] 80%、95%、100% 告警和熔断状态有明确反馈、可操作下一步和恢复路径。
- [ ] 静态 Token 预估与运行账单分离，估算值不会冒充真实消耗。
- [ ] 目录、Skill、Workflow 臃肿指标有统一单位、默认阈值和项目级覆盖入口。
- [ ] 轻度提示、中度草稿、重度阻断新激活的处理分级可追溯。
- [ ] 臃肿治理不会静默改写 Skill、Workflow 或项目源文件。
- [ ] 质量、预算和臃肿是三个独立状态，UI 不用一个总分替代它们。
- [ ] 技能库支持排序、筛选、分页/虚拟滚动和指标下探。

## 17. 不在本任务范围

- 不实现远程团队预算服务和跨设备强一致额度锁。
- 不实现自动模型切换或自动购买/扩容。

- 不实现 Skill/Workflow 自动改写、自动删除或无确认拆分。

## 18. 已确认决策

1. 质量评估拆为规范性、可用性、健康度、Token 能效、臃肿度、项目适配六个维度，同时显示置信度和覆盖率。
2. 缺少有效证据时允许显示静态分或未知，不伪造运行健康和 ROI。
3. Token 按 Provider、Harness、结构化日志、本地估算分级去重，禁止同一 Run 重复累计。
4. 个人会话、项目共享、后台监控和 Harness 实例采用独立预算池，并使用 80%/95%/100% 告警与熔断。
5. 跨设备/跨成员项目预算在本地应用中只能做策略提示和本地执行限制，不能宣称全局强一致。
6. 目录深度 4、单目录 20 个 Skill、单 Workflow 10 个节点等作为可配置默认阈值，而不是硬编码行业标准。
7. 臃肿治理采用轻度提示、中度生成草稿、重度阻断新版本激活，禁止静默改写正式内容。
8. 质量、预算、臃肿三类状态独立展示，技能库和报告支持排序、筛选、分页/虚拟滚动与证据下探。

本任务已接受，质量评分、Token 预算、熔断和臃肿治理实现必须遵守以上协议。
