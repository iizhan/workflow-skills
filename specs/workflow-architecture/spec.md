# 功能规格说明：Workflow 架构与注册协议

**功能标识**: `workflow-architecture`
**创建日期**: 2026-07-22
**状态**: TASK-WF-01 至 TASK-WF-06 已验收；TASK-WF-07A 已实现并通过真实无副作用 E2E，待用户验收
**任务通道**: controlled
**需求版本**: v1
**原始需求**: 支持未来大量 Workflow，并以可治理、可组合、可升级的方式接入场景化 Loop Engineering。

## 1. 背景与目标

当前工程已有以 `AGENTS.md`、项目 Skill、`workflow-state.yaml`、声明图谱和会话链路为基础的工程工作流。`TASK-06` 已定义 Workflow 图、版本和运行证据边界，但尚未定义：

- 多个角色、场景、项目 Workflow 如何分层与组合；
- Workflow 模板、项目绑定和实际运行之间的稳定身份；
- 场景质量循环如何在不产生第二套任务状态机的前提下工作；
- 如何让旧项目、旧声明和后续 Workflow 版本安全共存。

本任务建立一个可演进的 Workflow 控制平面。它使产品能够安全管理大量 Workflow，而不是把每个新流程做成互相复制的 Markdown 规则。

### 1.1 本次目标

1. 固化 Skill、Workflow Template、Project Binding、Workflow Run 与 Scenario Loop Run 的边界。
2. 定义分层、组合、路由、版本、兼容和废弃协议。
3. 定义场景化 Loop Engineering 的受控循环、质量门禁、预算和停止规则。
4. 为桌面端的工作流库、项目详情、流程图、脑图、运行链路和评测建立统一数据契约。
5. 保持旧项目和 `TASK-06` 既有声明、图谱和历史证据可读。

### 1.2 本次不做

- 不让桌面端绕过 Codex、Claude 或其他 Harness 去执行任意 Shell、脚本或 Prompt。
- 不自动修改项目业务代码、Workflow、长期记忆或远程资源。
- 不在本任务中一次性实现全部角色和场景 Workflow。
- 不把推断日志伪装成精确的 Workflow 执行事实。

## 2. 用户场景与验收

### 场景 1：运营大量通用 Workflow

作为 Workflow 维护者，我需要把基础、角色、场景和项目覆盖规则分层管理，避免创建大量重复流程。

验收：

1. 每个 Workflow 都能声明稳定 ID、版本、类型、适用条件、依赖 Skill、输入输出、门禁和兼容范围。
2. 场景 Workflow 只能组合已治理的 Skill、门禁和子 Workflow，不能嵌入任意执行脚本。
3. 工作流之间的依赖、冲突与版本不兼容能在应用前被检测。

### 场景 2：为一个项目绑定适用流程

作为项目使用者，我需要看到项目正在使用哪个 Workflow 版本、为什么适用、缺少哪些配置，以及升级会影响什么。

验收：

1. 项目绑定固定 Template ID、Template Version、项目覆盖层和绑定状态。
2. 升级必须预览差异、兼容性和回滚点，不能静默替换已激活版本。
3. 旧项目没有机器声明时仍可被读取为只读推断声明，不会被自动改写。

### 场景 3：运行场景化工程 Loop

作为研发人员，我需要让“设计稿到前端”、“设计稿到 API”、“Swagger 联调”等场景在已确认范围内自动完成分析、设计、计划、实施、验证、自测和修复循环。

验收：

1. 每个场景 Loop 有轮次、预算、根因、策略、验证证据和明确停止状态。
2. 只有已批准范围内的修复可自动继续；范围变化、权限、数据迁移、外部写入或发布必须重新确认。
3. 总分达到 90 不能绕过阻塞缺陷、未验证验收项和关键维度最低分要求。

### 场景 4：追溯与改进

作为管理者，我需要在桌面端查看一个 Workflow 的声明、项目绑定、实际运行、循环次数、质量趋势和改进候选。

验收：

1. 声明图、运行图和差异图继续保持分层，精确证据与推断证据可区分。
2. 每次 Loop 都可下探到 Skill、版本、命中原因、验证证据和停止原因。
3. 重复问题只能形成 Workflow 升级提案，不能自动改写全局规则。

## 3. 业务规则与边界

- Skill 是原子能力；Workflow 是组合、路由和门禁；Loop Engineering 是 Workflow 可选使用的运行时质量收敛能力。
- `AGENTS.md` 中的正式确认、影响范围、验证报告和用户验收仍是任务治理真值。
- 一个用户请求最多自动选择一个主场景 Workflow；其他流程只可作为显式依赖或后续场景。
- 所有激活版本不可原地修改；变更必须形成草稿版本、差异预览、确认和回滚点。
- 运行数据默认只保存摘要、哈希和证据引用，原始内容遵循既有隐私授权与生命周期规则。
- Workflow 默认以单项目为边界；跨项目统计仅聚合指标，不共享运行上下文、记忆或权限。

## 4. 事项清单

### ITEM-WF-001：Workflow 分层与声明契约

- 目标：定义机器可读 Manifest、Workflow 类型、组合和质量门禁。
- 验收：Manifest 可被静态校验；未声明的依赖、循环、权限和兼容问题有明确错误。

### ITEM-WF-002：Workflow Registry 与项目绑定协议

- 目标：定义模板、项目绑定、版本锁定、迁移与回退的稳定身份。
- 验收：同一 Template 在多个项目中可隔离绑定；旧声明保持可读；升级需要确认和回滚点。

### ITEM-WF-003：场景 Loop Engineering 协议

- 目标：定义场景 Loop 的状态、轮次、评分、预算、修复和停止机制。
- 验收：Loop 不与现有任务状态机冲突；重复失败不会无上限自转；质量分数不能绕过硬门禁。

### ITEM-WF-004：验证、迁移与可观察性

- 目标：定义静态校验、模拟、沙箱、试点、运行证据和桌面端展示协议。
- 验收：每一个 Workflow 版本都有可追溯验证证据和明确兼容状态。

## 5. 成功标准

- **SC-001**：新增 Workflow 不需要新增一套独立状态机或重复全局工程规则。
- **SC-002**：旧 `TASK-06` Workflow 声明与历史 Run 不丢失、不被静默升级。
- **SC-003**：新场景 Workflow 能表达确认门禁、有界 Loop、质量门禁和依赖关系。
- **SC-004**：桌面端和 Harness 都可以通过同一稳定 ID、版本和证据引用解释流程。
- **SC-005**：运行时不会因一次失败无限重试、无限加载 Workflow 或跨项目泄露上下文。

## 6. 已确认约束与后续确认事项

- 本版本默认以 `90` 作为场景质量评分阈值；各场景质量维度与最低分在后续场景包中定义。
- 本版本默认每个场景最多 `3` 轮完整循环、同一根因最多 `2` 种修复策略；两者均可在项目覆盖层收紧，不能放宽到无限。
- 本期 TASK-WF-01 已实现 Manifest 1.1、静态校验、只读模板 Registry 和 CLI/Doctor 集成；TASK-WF-02 已实现桌面端主进程的本地模板索引、项目绑定 Preview-Confirm-Apply-Verify、版本锁定与回滚快照。
- TASK-WF-03 已实现 Scenario Loop Run 的本地状态、轮次、根因/策略、质量与硬门禁、预算摘要、停止原因和演进候选协议；它不执行 Harness，也不改写项目业务代码或长期 Workflow/Skill。
- 独立的桌面端“工作流库”、项目 Binding/Loop 只读可视化、流程图与脑图已交付；真实 Harness 自动编排仍属于后续独立任务。
- `TASK-WF-05` 已实现受控 Harness JSONL 事件接入：只有带 Adapter/Harness、项目、Session、Turn 和无原文隐私声明的信封才可形成精确链路；该能力不安装 Hook，也不启动 Harness。
- `TASK-WF-06` 已验收：项目安装、Codex 目录连接和 Skill 观测各自独立显示；精确接入仅提供本地 JSONL 导入预览，不配置 Hook、App Server 或全局 Codex。
- `TASK-WF-07A` 已实现本机 Codex App Server 受控观测 POC，并完成真实无副作用 E2E：`ephemeral` Thread 在 `readOnly` 沙箱和 `never` 审批下完成，Thread、Turn、Item、Token 生命周期均可接收，未观察到命令或文件变更 Item，目标项目 Git 状态保持不变。当前 `0.131.0` Schema 未提供官方显式 Skill 调用事件，因此 Skill 证据仍保持推断。
