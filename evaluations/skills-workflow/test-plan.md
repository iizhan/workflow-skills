# Skills Workflow Test Plan

## Purpose

This plan verifies `project-engineering-workflow` and the Skill OS desktop application without confusing static rules, imported runtime evidence, and AI-assisted review.

The evaluation target is successful only when the workflow is proportionate, traceable, safe, and demonstrably useful on real tasks. A static score alone is never evidence that a model followed the workflow.

## Test Layers

| Layer | What it proves | Commands or evidence | Cannot prove |
| --- | --- | --- | --- |
| Contract | Required rules, gates, templates, and routing declarations exist | `check-contract.mjs`, `evaluate-task-requirements.mjs` | Live model adherence |
| Package | Generated project contains valid workflow assets | starter smoke, doctor, workflow manifest tests | Task outcome quality |
| Desktop service | Local indexing, trace, workflow, loop, model configuration contracts work | workbench typecheck, smoke, integration scripts | Provider quality or user outcome |
| Runtime replay | A harness produced observed traces, tool calls, tests, and outcome evidence | Codex/Claude session trace and project test output | Generalization beyond sampled tasks |
| AI-assisted review | A configured evaluator generated useful candidate tests for a selected source | Model configuration, provider response, human review | Execution of a Skill or workflow |

## Preconditions

1. Use a disposable fixture project for destructive or migration scenarios.
2. Bind only that project directory in Skill OS. Do not run whole-computer scans.
3. Record the workflow version, project Profile fingerprint, harness, model, input/output tokens, and test command before each runtime replay.
4. For an external evaluator, save an OpenAI-compatible endpoint and Key in Settings, test its connection, then explicitly enable selected-source upload. Do not upload credentials, telemetry, or whole-project source.
5. A candidate test generated by AI must be reviewed by a human before it enters a release gate.

## Metrics And Gates

| Metric | Formula or source | Release gate |
| --- | --- | --- |
| Contract coverage | Deterministic requirements passed / total | >= 90/100; no required security, scope, or verification failure |
| Routing precision | Correct target route / all evaluated routes | >= 90% across runtime replay cases |
| False-positive rate | Unrelated target invocations / negative cases | <= 10% |
| Confirmation compliance | Controlled changes with recorded approval before code / controlled changes | 100% |
| Verification evidence coverage | Completed cases with command, result, residual risk, and trace / completed cases | 100% |
| Runtime success rate | Completed non-cancelled runs / observed runs | >= 90%, with failures classified |
| Token efficiency | Candidate task tokens / baseline task tokens | Small tasks normally <= 1.20x; review any regression |
| Context budget | Estimated active bundle tokens | Must meet bundle hard limits before release |
| AI case usefulness | Human-approved candidate cases / generated cases | >= 70%; lower scores become an evaluator prompt improvement item |
| Real behavior confidence | Explicit observed trace evidence / all assertions | 100% for claims labeled "verified"; inferred evidence stays labeled inferred |

## Current Baseline: 2026-07-23

- Static workflow contract: pass.
- Task requirement contract coverage: `100 / 100`; it explicitly reports that live behavior is not measured.
- Workflow manifests, fixture doctor, desktop typecheck, desktop smoke, workflow registry, scenario loop, trace, harness-event, adapter-readiness, Codex app-server observation, and model-evaluation integrations: pass.
- Production build and source/renderer UI contract: pass. Electron window-click automation is blocked by the current macOS sandbox before a window is created; it is not counted as a visual-click pass.
- Token budget hard gate: pass. Active estimates are `fast-task 2622 / 3500`, `ordinary-dev 3450 / 3500`, `frontend 4751 / 5000`, `backend 4848 / 5000`, and `security 4635 / 5000`. They remain above soft warning thresholds, so real task telemetry must validate progressive routing before a performance claim.

## Budget Follow-up

1. Keep fast tasks narrow; load confirmation, role standards, and verification detail only when lane and impact require them.
2. Record provider-reported input/output/cache Tokens for each runtime replay and compare the task route with its baseline.
3. Treat a soft-budget warning as an architecture review signal, not a release pass or fail on its own.
4. Rerun `node evaluations/skills-workflow/scripts/estimate-token-cost.mjs --enforce` whenever core Skills or bundle composition changes.

## Recording A Runtime Replay

For each real case, save a record based on `templates/run-record.md` and include:

- task and expected lane
- selected Skill/workflow version and project Profile state
- confirmation and scope artifacts where applicable
- commands, tests, screenshots, and trace identifiers
- input, output, cached, reasoning, and total Tokens when the harness exposes them
- user acceptance, residual risk, and dissatisfaction category if any

Use `templates/scorecard.md` and `templates/token-economics.md` for the final comparison. AI-generated cases are only an input to this record; they cannot close the case themselves.
