# 参考项目工程化能力拆解

本文档总结以下项目的工程化能力：

- `claude-skills-main`
- `project-root`
- `project-teardown-skill-main`
- `spec-kit-skills-agent-starter`
- `hermes-web-ui`

## 1. `claude-skills-main`

代表能力：

- skill 包装最小闭环清晰：`SKILL.md` 就是入口
- 单个 skill 职责单一，便于复制、安装、组合
- 触发条件和示例 prompt 写得直接，接入门槛低

工程化启发：

- 好的工程化不一定先从大而全开始
- 最先要解决的是“能力如何被稳定调用”
- 复用单元越明确，跨项目复制越容易

## 2. `project-root`

代表能力：

- 项目级 `agent.md` 统一调度规则
- `docs/00_INDEX.md` 形成知识入口
- `任务类型 -> 必读文档` 的映射非常强
- `危险区`、`排障`、`技术方案`、`编码规范` 都被显式建模

工程化启发：

- 工程化的核心不是模板，而是“先读什么、后做什么、哪些不能乱动”
- 文档如果不能服务任务路由，就只是静态知识库
- 团队规则必须能转成 AI 和人都能执行的门禁

## 3. `project-teardown-skill-main`

代表能力：

- 强调“为什么逼出这个设计”，而不是只列技术名词
- 重视逐层拆解、约束、边界、取舍
- 有明显的架构判断训练目标

工程化启发：

- 研发流程不能只有实施，还要有架构理解能力
- 新人或 AI 进入陌生项目时，先建立“设计因果链”比直接改代码更重要
- Onboarding 不是看目录，而是理解关键机制为什么存在

## 4. `spec-kit-skills-agent-starter`

代表能力：

- `AGENTS.md + .agents/skills + .specify + specs/` 的四层结构
- 从需求、规格、方案、任务到实现与验证形成闭环
- 模板化渲染，支持快速接入任意项目
- 通用流程规则与项目特有规则分层管理

工程化启发：

- 这是最接近“可复制项目工程底座”的做法
- 真正可落地的工程化一定要把流程资产与业务资产拆开
- 快速接入能力来自模板、脚本和最少必调项，而不是大篇幅说明

## 5. `hermes-web-ui`

代表能力：

- 真实复杂项目已把 Agent 工作流接入主仓库
- `AGENTS.md` 中的门禁链路完整，包含需求、范围、方案、实现、测试、审查、安全、文档
- 工程结构清楚：`packages/client`、`packages/server`、`.specify`、`tests`
- 测试面广，说明流程不是停留在文档层

工程化启发：

- 好的工程化必须在真实复杂系统中仍能跑通
- 项目级 skill 不该只服务“生成代码”，还要服务 review、domain boundary、security、docs sync
- spec 流程如果不连接真实测试和真实交付，就只是纸面流程

## 汇总结论

这几个项目合起来，能抽象出一套高质量工程化能力模型：

1. 入口层：要有统一的项目级调度入口，例如 `AGENTS.md`
2. 能力层：要有职责清晰的本地 skills，而不是把所有规则堆进一份超长文档
3. 工件层：要有 `spec / plan / tasks / checklist` 这样的中间产物来防止需求漂移
4. 约束层：要有范围锁定、危险区、代码规范、架构边界
5. 交付层：要有测试、review、文档同步、剩余风险说明
6. 迁移层：要能通过模板和脚本快速复制到任何项目

本 skill 项目就是按这 6 层抽象设计的。
