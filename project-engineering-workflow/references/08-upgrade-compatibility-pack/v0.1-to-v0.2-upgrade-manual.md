# v0.1 to v0.2 Upgrade Manual

This manual explains how an existing project that already uses an older `project-engineering-workflow` starter should upgrade to the `0.2.x` line without breaking existing generated artifacts.

## Goal

Upgrade the workflow layer safely while preserving the usability of older artifacts already present in the project.

This manual assumes:

- the project already has a baseline workflow starter
- old `specs/<feature>/` artifacts already exist
- the team wants optional access to memory, evolution, reflection, and final-output capabilities

## Rule Zero

Do not rewrite existing `specs/<feature>/` artifacts by default.

That means:

- do not overwrite old `spec.md`
- do not overwrite old `plan.md`
- do not overwrite old `tasks.md`
- do not rewrite old `workflow-state.yaml` just to match the newest template

Use additive upgrade steps instead.

## Step 1. Run Doctor First

Run:

```bash
bash scripts/doctor.sh /absolute/path/to/target-repo
```

If you are validating from the workflow package source itself, you can also run:

```bash
npm --prefix project-engineering-workflow run doctor
```

To preview a safe additive upgrade, run:

```bash
npx @workflow-skills/project-engineering-workflow upgrade \
  --output-dir "/absolute/path/to/target-repo" \
  --mode capabilities \
  --dry-run \
  --write-report
```

Interpretation:

- `Doctor failed` means the project is missing baseline workflow files and should fix those first.
- `Doctor passed with upgrade suggestions` means the project is compatible and can adopt newer workflow files gradually.
- `Doctor passed` means the project already contains the full current starter set.

Important:

- adding some `v0.2` optional files does not by itself force the project into full `v0.2.x` completeness checks
- only adding `.specify/workflow-version.txt` signals that the project now claims the full current workflow line
- `upgrade` never modifies historical `specs/` artifacts; it only works on workflow-layer files
- `--write-report` can produce a reviewable Markdown upgrade report under `docs/`

Treat these as historical delivery records:

- `specs/<feature>/plan.md`
- `specs/<feature>/tasks.md`
- `specs/<feature>/quickstart.md`
- `specs/<feature>/workflow-state.yaml`

Only edit them when a real feature continuation or explicit migration requires it.

## Step 3. Upgrade In This Order

### Phase 1. Governance Only

Upgrade these first:

- `AGENTS.md`
- `.specify/memory/constitution.md`
- `docs/Codex团队开发说明.md`

Why:

- this lets the team understand the new rules
- it does not force old feature artifacts to change yet

### Phase 2. Add New Optional Capabilities

Then add:

- `project-memory-router`
- `project-evolution-router`
- new `.specify/memory/*` protocols
- `AI能力地图.md`
- `升级兼容策略.md`
- `.specify/workflow-version.txt` only after you intentionally adopt the full `v0.2.x` workflow set

Why:

- the project can start using the new lanes for future work
- old work remains untouched

### Phase 3. Add New Templates For Future Features Only

Then add:

- `reflection-template.md`
- `rule-change-template.md`
- `delivery-summary-template.md`

And update:

- `.specify/scripts/bash/create-feature.sh`

Why:

- new features will get the richer artifact set
- old features do not need to be rewritten

Important:

- do not add `.specify/workflow-version.txt` early
- only add it after the full `v0.2.x` optional file set is present
- otherwise `doctor` will correctly treat the project as an incomplete current-line upgrade

### Phase 4. Trial One Real Feature

Pick one new or currently active feature and try:

- `task-reflection.md`
- `rule-change-proposal.md`
- `delivery-summary.md`

Only after that trial succeeds should the team promote the new artifacts into normal practice.

## Step 4. Handle workflow-state.yaml Carefully

For old `workflow-state.yaml` files:

- do not overwrite them from the new template
- if a live feature needs the new fields, add only the missing fields manually
- keep all old fields untouched

Safe additions in `0.2.x` include:

- `session_reflections`
- `reflection_artifacts`
- `delivery_artifacts`
- `memory_candidates`
- `rule_change_candidates`
- `memory_updates`
- `evolution_updates`

For `.specify/memory-store/`:

- do not overwrite existing durable memory records during starter upgrades
- if the starter adds a new index or schema file, add it alongside the existing data
- index rebuild is allowed; record rewrite is not the default

## Step 5. Files That Can Stay Old For A While

A project can still function without immediately adopting:

- `project-memory-router`
- `project-evolution-router`
- `task-reflection.md`
- `rule-change-proposal.md`
- `delivery-summary.md`

The tradeoff is simply that the project will not yet benefit from those new lanes.

## Step 6. What Not To Do

Avoid these upgrade mistakes:

- do not bulk replace every file under `specs/`
- do not rewrite all old `workflow-state.yaml` files from the latest template
- do not treat missing v0.2 files as a reason to block all work
- do not introduce a major-process change into an old project without team confirmation

## Suggested Upgrade Checklist

Use this short checklist:

1. Run `doctor`
2. Fix baseline issues first
3. Add governance updates
4. Add optional new lanes
5. Use new templates only for new or active features
6. Trial one real feature
7. Roll out gradually

## Bottom Line

Upgrade the workflow like a schema migration:

- additive first
- rewrite only when necessary
- preserve old records
- validate on one real feature before broader rollout
