# v0.2 to v0.3 Upgrade Manual

This manual explains how a project already on the `0.2.x` workflow line should adopt the `0.3.x` branch and release capability without breaking older generated artifacts.

## Goal

Add governed git flow support:

- `feature/<feature-slug>`
- `release/<version>`
- `v<version>`
- merge to `main`

without forcing old `specs/<feature>/` artifacts to be rewritten.

## Rule Zero

Do not treat missing branch/release assets as a reason to block ordinary work on an older `0.2.x` project.

For `0.3.x`, branch/release should be adopted like any other additive workflow capability:

- trial first
- validate on one real feature or release
- promote later

## What Changes In v0.3

Recommended new assets:

- `.agents/skills/project-branch-release/SKILL.md`
- `.specify/release/release-policy.md`
- `.specify/scripts/bash/create-feature-branch.sh`
- `.specify/scripts/bash/prepare-release.sh`
- `.specify/scripts/bash/finalize-release.sh`
- `.specify/templates/release-checklist-template.md`
- `.specify/templates/release-notes-template.md`

Also updated:

- `AGENTS.md`
- `workflow-state.yaml` template
- docs that describe the capability map and workflow order

## Step 1. Run Doctor First

Run:

```bash
bash scripts/doctor.sh /absolute/path/to/target-repo
```

Then preview the additive upgrade:

```bash
npx @workflow-skills/project-engineering-workflow upgrade \
  --output-dir "/absolute/path/to/target-repo" \
  --mode capabilities \
  --dry-run \
  --write-report
```

And template-side preview:

```bash
npx @workflow-skills/project-engineering-workflow upgrade \
  --output-dir "/absolute/path/to/target-repo" \
  --mode templates \
  --dry-run \
  --write-report
```

Interpretation:

- `Doctor passed with upgrade suggestions` is the expected state for a healthy `0.2.x` project that has not adopted the new branch/release files yet.
- only after `.specify/workflow-version.txt` is intentionally updated to `0.3.0` should doctor require the full current-line branch/release file set.

## Step 2. Upgrade In This Order

### Phase 1. Governance

Add or review:

- `project-branch-release`
- `release-policy.md`
- updated `AGENTS.md`
- updated team docs

Why:

- the team first agrees on the flow
- old feature artifacts remain untouched

### Phase 2. Branch / Release Scripts

Add:

- `create-feature-branch.sh`
- `prepare-release.sh`
- `finalize-release.sh`

Why:

- new work can start using the governed branch flow
- old work does not need bulk edits

### Phase 3. Future Templates Only

Add:

- `release-checklist-template.md`
- `release-notes-template.md`
- updated `workflow-state.yaml` template
- updated `create-feature.sh`

Why:

- new features and new releases gain the richer flow
- old feature workspaces remain valid

### Phase 4. Trial One Feature And One Release

Try this sequence on one real change:

1. `bash .specify/scripts/bash/create-feature.sh <feature-slug> "<Feature Name>"`
2. finish implementation, review, and test report
3. `bash .specify/scripts/bash/prepare-release.sh <version>`
4. update release checklist and release notes
5. `bash .specify/scripts/bash/finalize-release.sh <version>`

Only after this trial works should the team treat `0.3.x` branch flow as the default rule.

## Step 3. When To Write workflow-version.txt

Do not update `.specify/workflow-version.txt` to `0.3.0` early.

Only do it after:

- governance files are in place
- branch/release scripts are present
- release templates are present
- one real pilot succeeded

Once the project declares `0.3.0`, doctor will correctly expect the full current branch/release asset set.

## Step 4. What Not To Do

- do not rewrite every old `workflow-state.yaml`
- do not bulk add release artifacts to every historical feature
- do not force old releases to retroactively match the new branch flow
- do not merge branch/release governance as a hidden breaking change

## Bottom Line

Upgrade `0.2.x -> 0.3.x` the same way as a safe schema migration:

- additive first
- pilot on one real flow
- declare the version only after adoption
- keep old feature artifacts usable
