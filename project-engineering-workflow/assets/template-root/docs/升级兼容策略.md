# __PROJECT_NAME__ 升级兼容策略

这份文档用于约束 workflow starter 的升级方式，避免新版本破坏旧项目已经生成的工件。

## 核心原则

### 1. 默认增量，不默认重写

升级 starter 时，默认只新增能力，不静默重写已有项目中的既有工件。

- 可以新增新的 skill、模板、协议、文档和状态字段
- 不应在 minor 版本中直接删除、重命名或强制替换旧工件

### 2. 旧工件优先兼容读取

如果历史项目缺少某个新文件，workflow 应优先：

- 降级使用旧路径
- 提示“可选升级”
- 避免把缺失新文件当成硬错误

### 3. 旧产物不应因升级而失效

已有项目中的下列产物必须尽量保持可继续使用：

- `spec.md`
- `plan.md`
- `tasks.md`
- `quickstart.md`
- `workflow-state.yaml`
- 已存在的 `specs/<feature>/` 工件

### 4. 状态文件只做向后兼容扩展

对于 `workflow-state.yaml`：

- minor 版本只能新增字段
- 不应在 minor 版本中删除旧字段
- 不应改变旧字段的含义
- 新逻辑必须容忍旧字段缺失

对于 `.specify/memory-store/`：

- minor 版本只能新增 schema 字段或重建轻索引
- 不应在 minor 版本中静默重写 durable memory 正文
- durable memory 应视为项目数据，不应被 starter 模板覆盖

### 5. 模板升级与项目升级分离

starter 模板的升级不等于旧项目自动迁移。

- 模板可以演进
- 项目是否吸收新模板，必须由一次明确升级动作决定

## 版本规则

### Patch

适合：

- 文案修正
- 说明补充
- 非破坏性脚本修复

要求：

- 不新增必须文件
- 不改变现有流程顺序

### Minor

适合：

- 新增可选能力链
- 新增模板、协议、样例和文档
- 新增可选状态字段

要求：

- 新文件默认作为可选升级项
- `doctor` 对旧项目应通过并提示升级建议
- 旧项目不应因缺失新文件而直接失败
- 旧项目即使先吸收部分新文件，只要未声明当前版本标记，也不应被当作不完整升级

### Major

适合：

- 删除旧工件
- 重命名核心文件
- 调整主流程顺序
- 改变关键状态字段含义

要求：

- 必须提供迁移说明
- 必须明确 breaking changes
- 必须要求用户显式执行迁移动作

## 升级动作建议

对已经使用本 starter 的项目，推荐按以下顺序升级：

1. 先运行 `doctor`
2. 看“缺失的是基础文件还是可选升级文件”
3. 先确认是否真的需要新能力
4. 以 feature 为单位试点吸收新工件
5. 验证通过后再逐步推广到团队默认流程

## 当前 v0.2、v0.3、v0.4、v0.5 与 v0.6 的兼容结论

`v0.2` 新增的 memory、evolution、reflection、final-output 能力，应该被视为：

- 对新项目：默认生成
- 对旧项目：可选升级，不应破坏既有产物

`v0.3` 新增的 branch/release 能力，应该被视为：

- 对新项目：默认生成
- 对旧项目：可选升级，不应因为缺失 `feature/* -> release/* -> tag -> merge main` 资产而阻断旧 workflow

`v0.4` 新增的自适应任务通道、版本化确认、完整影响分析和用户验收闭环，应该被视为：

- 对新项目：默认生成并声明 `0.4.0`
- 对旧项目：原有 `specs/` 和状态文件继续可读；只有显式升级 governance/templates 后才采用新门禁
- `doctor`：仅对声明为 `0.4.x` 的项目检查新确认与影响契约，不把 `0.3.x` 项目误判为损坏
- 覆盖已有 workflow 文件前：必须先查看 dry-run 差异并显式使用 `--overwrite-existing`

`v0.5` 新增的后端/前端角色 Workflow，应该被视为：

- 对新项目：默认生成
- 对旧项目：新增角色入口和 references 作为可选升级，不强制重写既有项目规则
- 角色入口只负责按 Profile 和变更信号路由，不复制 Core Workflow 的确认门禁

`v0.6` 新增的项目 Profile、架构摘要、决策记忆和证据指纹，应该被视为：

- 对新项目：默认生成 `pending_analysis` Profile，首次研发任务完成分析后变为 `ready`
- 对旧项目：先以可选能力升级，不因缺失 Profile 把 `v0.5.x` 项目判为损坏
- Profile 刷新只写项目认知缓存，不改业务资产、不复制敏感信息、不自动提交
- `decision-memory.yaml` 只保存明确确认的稳定项目选择；不能复用为权限、删除、发布、范围或验收批准
- 证据变化时优先按模块刷新，避免每次任务重新扫描整个项目

## 一句话原则

> 新版本可以让未来项目更强，但不能让已经生成的旧项目工件突然失效。
